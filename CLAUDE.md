# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

Bilingual (es/en) static portfolio site — Astro 7 + Tailwind v4, no framework islands, no backend. Published at `https://portafolio.daaptech.org`. Two build-time side products are generated by scripts and **committed to the repo**: QR PNGs for project links and PDF versions of the CV pages.

Active branch is `cloud_version` — both GitHub workflows trigger on it, not on `main`.

Content, identifiers, folder names and comments are in Spanish (`proyectos`, `seccions/`, `raizApp`, `sobremi`). Match that when adding code.

## Commands

```bash
pnpm run dev        # dev server on :4321
pnpm run build      # astro check && astro build
pnpm run preview    # serve dist/ on :4321
npx astro check     # type check only

pnpm run GQR        # regenerate public/img/qr/*.png from cv.js
pnpm run GPDF       # print /es/cv and /en/cv to public/docs/*.pdf (needs a server already running)
```

There is no test suite; `astro check` is the only automated verification. Note that section components take `infoSeccion: any`, so type checking catches very little in the data path.

`GPDF` fetches `http://localhost:4321/{es,en}/cv` — start `pnpm run preview` (or `dev`) in another shell first. Setting `PROD=true` makes it print the live production site instead.

`pnpm-workspace.yaml` disables postinstall builds for puppeteer/esbuild/sharp, so Chrome is not downloaded on install. If `GPDF` fails to find a browser, install it explicitly: `npx puppeteer browsers install chrome`.

Lockfiles are gitignored (`pnpm-lock.yaml`, `package-lock.json`), so CI resolves dependencies fresh within the semver ranges in `package.json`.

## Architecture

### Content → presentation → page pipeline

Three layers, all under `src/cv_info/`:

1. **`cv.js`** (~850 lines) — the single source of truth. Exports two parallel objects, `es` and `en`, with identical shape (`sobremi`, `experiencias`, `gradosCompletados`, `certificados`, `publicaciones`, `habilidades`, `proyectos`, `referencias`, `previewFooter`). Editing one language without the other silently desyncs the site. Also exports `raizApp` and `rutaQR`, the path prefixes every asset URL is built from.

2. **`es.js` / `en.js`** — presentation layer. They import the raw data and bind it to Astro components, icons and Tailwind class strings, exporting `navItems`, `footerInfor`, `ui` (translation strings) and `pagIndex`. The key structure is `seccionItems`: each entry is `{navitems, name, icon, classSeccion, classTittle, classIcon, seccion, seccionInfo}` where `seccion` is the component itself and `seccionInfo` the data slice it receives.

3. **`src/pages/{es,en}/index.astro`** — generic renderers. They map over `pagIndex.secciones` and emit `<bloque.seccion infoSeccion={...} ui={ui} />`. **Adding, removing or reordering a homepage section means editing `seccionItems` in `es.js` and `en.js`; the page files rarely change.**

`src/pages/index.astro` is a copy of `es/index.astro` serving the site root (Spanish is the default locale but still prefixed).

### The CV pages are a separate world

`src/pages/{es,en}/cv.astro` (~410 lines each) bypass `Layout.astro` and all components entirely: standalone HTML with a large inline `<style>` block (21cm container, `@media print` with explicit `break-inside`/`break-after` rules) and FontAwesome from a CDN. They read `es`/`en` from `cv.js` directly. The two files are near-duplicates — any change must be mirrored, and both are what Puppeteer prints to PDF. The print CSS is tuned to control page breaks; changing spacing there reflows the committed PDFs.

### Base paths

`config.js` holds prod/dev values; `raizApp` (from `cv.js`) and `base` (in `astro.config.mjs`) both derive from it via `import.meta.env.PROD`. Build asset URLs as `raizApp + "img/..."` rather than hardcoding a leading `/`.

### i18n

Astro i18n: `defaultLocale: 'es'`, `prefixDefaultLocale: true`, so both `/es/` and `/en/` are prefixed. Language switching is a plain link — each page computes `rutaLeng` pointing at the other locale and passes it to `NavBar`.

`src/i18n/ui.ts` and `src/i18n/utils.ts` are leftovers from the upstream template and are **imported nowhere**. The live translation table is the `ui` object exported from `cv_info/es.js` / `en.js`, threaded through as props (`Layout` → `NavBar` → `ThemeToggle`, page → section components). Add UI strings there, not in `src/i18n/`.

### Dark mode

Tailwind v4 with no `tailwind.config.*` file — the entire config is `src/styles/global.css`:

```css
@import "tailwindcss";
@variant dark (&:where(.dark, .dark *));
```

So `dark:` utilities depend on a `.dark` class on `<html>`, set by the inline script in `ThemeToggle.astro` from `localStorage.theme` (`light`/`dark`/`system`). Several component `<style>` blocks still use `@media (prefers-color-scheme: dark)` (`Layout.astro`, `NavBar.astro`) — those follow the OS, not the toggle. Prefer `dark:` utilities for anything that must respond to the toggle.

### Generated assets

- **QR codes** — `src/scripts/url_to_qr.js` walks only the **`es`** data (`es.proyectos[].github`, `es.certificados.link`, `es.publicaciones[0].link`) and names files from the Spanish title (`qr_<title with spaces → _>.png`). The `en` project entries point at those same Spanish-named files. Renaming a Spanish project title therefore requires re-running `GQR` and updating the `qr:` field in **both** `es` and `en`.
- **PDFs** — `src/scripts/pdf_cv.js` writes `public/docs/CV_ESP.pdf` and `CV_EN.pdf` with a custom header/footer template (page numbers).

## Content-change workflow

1. Edit `src/cv_info/cv.js` — both `es` and `en`.
2. Run `pnpm run GQR` if any project/certificate/publication URL or Spanish project title changed.
3. `pnpm run build`, then `pnpm run preview` in a second shell, then `pnpm run GPDF`.
4. Commit to `cloud_version`. CI will regenerate the PDFs anyway (step 3 is for local verification).

## CI/CD

`.github/workflows/deploy.yml` (push to `cloud_version`): `dorny/paths-filter` watches `src/cv_info/cv.js` and both `cv.astro` files; on a hit it installs, builds, starts `preview`, runs `GPDF`, and auto-commits the regenerated PDFs back to `cloud_version` with the message `Update PDFs` — that's the source of the repeated "Update PDFs" commits in the log. The workflow uses `npm install` even though local development is pnpm.

Despite its name, this workflow does **not** deploy — the Cloudflare deploy is wired up outside the repo (Cloudflare Pages Git integration).

`.github/workflows/codeql.yml` runs CodeQL on push/PR to `cloud_version` and weekly.
